# اجرای نورا با Docker

این فولدر باید کنار چهار فولدر پروژه باقی بماند؛ سورس‌ها داخل آن کپی نشده‌اند:

```text
noora/
  docker/
  noora_frontend/
  noora-flow/
  nait-templates/
  nait-diagrams/
```

Docker با Linux containers و Compose نسخه 2.24 یا جدیدتر لازم است.

## اجرا

از ریشه پروژه:

```powershell
cd docker
docker-compose up -d
```

دستور معادل: `docker compose up -d`. بدون `-d` لاگ‌ها در همان ترمینال نمایش داده می‌شوند.

روی سیستم خودتان: http://localhost:3000

روی سرور: آدرس IP یا دامنه همان سرور با پورت 3000، مثلاً http://95.38.184.97:3000

نیازی به تغییر IP در env نیست. Nginx درخواست‌های `/backend/` و `/socket.io/` را به بک‌اند و بقیه درخواست‌ها را به فرانت می‌فرستد. فقط پورت 3000 روی میزبان منتشر می‌شود؛ پورت 4000 داخلی است. روی سرور پورت 3000 باید قابل دسترس باشد.

در هر `up`، تنظیم `pull_policy: build` ساخت ایمیج فرانت و بک‌اند را اجرا می‌کند و `no_cache: true` استفاده از لایه‌های کش قبلی را غیرفعال می‌کند. Compose کانتینرهای دارای ایمیج جدید را جایگزین می‌کند. نیازی به `down` قبل از اجرا نیست. ایمیج‌های زیرساختی MongoDB، Redis و Elasticsearch از رجیستری دریافت می‌شوند و دوباره ساخته نمی‌شوند. این تنظیم هر بار نصب وابستگی‌ها و کامپایل را تکرار می‌کند و زمان‌بر است.

برای اجبار به بازسازی کانتینر حتی در صورت یکسان بودن ایمیج نهایی:

```powershell
docker-compose up -d --force-recreate
```

Compose قدیمی نسخه 1 پشتیبانی نمی‌شود. تنظیم‌ها مطابق [مستندات سرویس‌های Compose](https://docs.docker.com/reference/compose-file/services/#pull_policy) و [تنظیم ساخت](https://docs.docker.com/reference/compose-file/build/#no_cache) هستند.

## تنظیمات

فایل `.env` تنظیمات Compose شامل آدرس عمومی، پورت، تگ ایمیج، حافظه Elasticsearch و رمزهای مشترک دیتابیس‌ها را دارد. `backend.env` تنظیمات برنامه را بر اساس فایل استقرار قبلی نگه می‌دارد و رمز دیتابیس‌ها را از `.env` می‌خواند. هر دو فایل در Git نادیده گرفته می‌شوند؛ هنگام انتقال این فولدر به سرور باید همراه آن باشند. تنظیمات اختیاری `backend.local.env` بر `backend.env` اولویت دارند. فایل‌های env پروژه‌های اصلی وارد ایمیج نمی‌شوند.

مقدار `NEXT_PUBLIC_APP_URL` خالی و `NEXT_PUBLIC_EXTERNAL_API_URL=/backend` است تا آدرس مرورگر مبنا باشد. برای تغییر پورت فقط `FRONTEND_PORT` را در `.env` تغییر دهید. `NEXT_PUBLIC_INTERNAL_API_URL=http://backend:4000` برای درخواست‌های سمت سرور فرانت استفاده می‌شود. متغیرهای عمومی هنگام build در فرانت قرار می‌گیرند. HTTPS به گواهی و تنظیم TLS جداگانه نیاز دارد؛ پیکربندی فعلی HTTP است.

MongoDB به صورت replica set تک‌عضوی با احراز هویت و keyfile پایدار اجرا می‌شود. Elasticsearch هم رمز دارد؛ ارتباط داخلی آن HTTP است. این تنظیم‌ها مطابق [راهنمای MongoDB](https://www.mongodb.com/docs/manual/tutorial/enable-internal-authentication) و [راهنمای Elastic](https://www.elastic.co/guide/en/elasticsearch/reference/current/security-minimal-setup.html) هستند. MongoDB، Redis و Elasticsearch روی میزبان پورت منتشر نمی‌کنند. رمزهای اولیه فقط هنگام ایجاد دیتابیس تازه اعمال می‌شوند؛ برای volume قدیمی، کاربر و رمز باید در خود دیتابیس نیز تنظیم شوند. تغییر env رمز کاربر موجود را عوض نمی‌کند و هیچ داده‌ای خودکار حذف یا مهاجرت داده نمی‌شود.

`APP_ENV` فعلاً `development` است؛ برنامه با خروجی کامپایل‌شده اجرا می‌شود، ولی کارهای زمان‌بندی‌شده مخصوص production فعال نمی‌شوند. برخی کارهای زمان‌بندی‌شده در کد مستقل از این مقدار فعال هستند.

کد فعلی زمان JWT را به ثانیه می‌خواند؛ معادل ۱۵ دقیقه و ۳۰ روز به ترتیب `900` و `2592000` تنظیم شده است. متغیرهای `SEED_SUPER_ADMIN_*` در فایل حفظ شده‌اند اما seeder فعلی آن‌ها را نمی‌خواند و مدیر اولیه ایجاد نمی‌کند. `BPMN_*`، `ACTIVITY_CANCEL_STATUS`، `ELASTIC_API_KEY` و کدهای سپیدار بدون پیشوند `NEXT_PUBLIC_` نیز برای سازگاری با فایل قبلی حفظ شده‌اند و در کد فعلی مصرف ندارند.

سرویس‌های جانبی با مقدارهای اولیه `0` و `localhost` فایل ارسالی تنظیم شده‌اند. این مقادیر اتصال واقعی یا غیرفعال‌سازی قابلیت نیستند؛ `localhost` داخل بک‌اند به همان کانتینر اشاره می‌کند. برای استفاده از پیامک، ایمیل، کپچا، درگاه و سایر اتصال‌ها باید مقدار واقعی سرویس وارد شود.

## فایل‌ها و داده‌ها

قالب‌ها در `/app/assets/templates` و نمودارهای مرجع در `/app/assets/diagrams` داخل ایمیج بک‌اند قرار می‌گیرند. ثبت فرایندها در دیتابیس خودکار نیست و باید از مسیر موجود برنامه انجام شود. نمودارهای آپلودشده برنامه در `/app/statics/bpmn` ذخیره می‌شوند. قالب‌هایی که در سورس موجود نیستند با Docker تولید نمی‌شوند.

دیتابیس‌ها و مسیرهای آپلود فایل volume مستقل دارند. پوشه قالب‌ها volume نیست تا تغییرات قالب با ایمیج جدید پوشانده نشود. داده‌های استقرارهای قبلی خودکار منتقل نمی‌شوند. ایمیج‌های قدیمی بدون استفاده خودکار حذف نمی‌شوند.

```powershell
docker-compose ps
docker-compose logs -f backend frontend
docker-compose down
```

`down` داده‌های volume را نگه می‌دارد؛ `down -v` آن‌ها را حذف می‌کند.

## خطای دریافت ایمیج Node (403)

اگر build روی خط `FROM` با خطای `failed to fetch anonymous token` و `403 Forbidden` از `auth.docker.io` متوقف شد، دریافت ایمیج پایه از Docker Hub مسدود شده است. این خطا پیش از اجرای `npm run build` رخ می‌دهد.

در `docker/.env` منبع جایگزین را تنظیم کنید؛ Compose آن را به هر دو Dockerfile ارسال می‌کند:

```dotenv
NODE_IMAGE=public.ecr.aws/docker/library/node:22-bookworm-slim
```

سپس از پوشه `docker`، دستور `docker compose up -d` را اجرا کنید. برای استفاده مستقیم از Docker Hub مقدار را به `node:22-bookworm-slim` تغییر دهید. تنظیمات دیتابیس و رمزها برای این خطا نیاز به تغییر ندارند.

## وضعیت بررسی

ساختار Compose با `docker compose config --quiet` و `docker-compose config --quiet` روی Compose نسخه 2.39.4 بررسی و تأیید شده است. موتور Docker هنگام آماده‌سازی در دسترس نبود؛ build ایمیج‌ها و تست اجرای کامل سرویس‌ها انجام نشده است.
